# VideoCall — видеозвонки, чат и секретные ссылки

Учебный пет-проект: клон Яндекс Телемоста. Групповые видеозвонки, чат-комнаты в реальном
времени и отдельные инструменты — одноразовые «секретные ссылки» и генератор ключей (оба с
шифрованием/генерацией на клиенте). Ставится как PWA (устанавливаемое приложение).

## Стек

| Слой | Технологии |
|---|---|
| Frontend | React 19 + Vite, Tailwind CSS 4, Zustand, React Router 7, socket.io-client, @livekit/components-react, vite-plugin-pwa |
| Backend | Node.js (ESM), Express 4, Sequelize + PostgreSQL, socket.io, livekit-server-sdk, jsonwebtoken, bcrypt |
| Инфраструктура | Docker Compose: PostgreSQL 16 + LiveKit (self-hosted SFU) |
| Тесты | node:test + supertest (отдельная БД `videocall_test`) |

## Архитектура

```
        Браузер (React SPA, Vite :5173)
        |         |                |
        | REST    | WebSocket      | WebRTC + WS (медиа)
        | (axios, | (socket.io,    |
        | cookie) |  cookie)       v
        v         v          +-----------------+
   +--------------------+    | LiveKit SFU     |
   | Express API :4000  |    | :7880 сигналинг |
   | REST + socket.io   |    | :7881 TCP-фолбэк|
   +--------------------+    | UDP 50000-50010 |
        |            \       +-----------------+
        v             \            ^
   +-------------+     \  подписывает access-токены
   | PostgreSQL  |      \ (LIVEKIT_API_KEY/SECRET)
   | :5432       |       +---------+
   +-------------+
```

- **Express** отвечает за REST (auth, комнаты, история чата, секреты) и socket.io
  (сообщения и presence в реальном времени) на одном HTTP-сервере.
- **LiveKit** гоняет само медиа (видео/звук) как SFU — Express медиа не касается,
  он только подписывает своим ключом токены доступа в конкретную комнату.
- **PostgreSQL** хранит юзеров, комнаты, сообщения и шифроблобы секретов.

## Основная логика

### Аутентификация

1. Регистрация: `POST /api/auth/register` → валидация (типы, формат email, пароль ≥ 6,
   имя ≤ 50) → `bcrypt.hash(password, 10)` → юзер в БД.
2. Сервер подписывает JWT `{ userId }` (срок 7 дней) и кладёт его в **httpOnly cookie** —
   JS на клиенте токен не видит в принципе.
3. Каждый защищённый REST-запрос проходит middleware `requireAuth`: cookie → verify JWT →
   юзер из БД → `req.user`. Socket.io делает то же самое один раз при подключении (`io.use`).
4. Клиент при старте дёргает `GET /api/auth/me`, чтобы узнать, жива ли сессия
   (Zustand-стор держит `user` + `loading`).
5. Logout стирает cookie. Email нормализуется (`trim().toLowerCase()`) и при регистрации,
   и при входе — `Test@mail.ru` и `test@mail.ru` это один аккаунт.

### Комнаты и чат

- Комната создаётся авторизованным юзером, получает читаемый код вида `abc-d2f`
  (`crypto.randomInt`, алфавит без похожих символов — легко продиктовать).
- Модель доступа — **«ссылка = доступ»**, как в Телемосте: любой авторизованный,
  знающий код, может войти. Списков участников/приглашений нет сознательно.
- История чата — по REST при входе (последние 100 сообщений), дальше realtime:
  `message:send` → сохранение в БД → `message:new` всем в комнате (включая отправителя —
  клиент своё сообщение локально не добавляет, ждёт эхо сервера).
- Список участников звонка берётся на клиенте из LiveKit (реактивно к publish/mute — сразу видно
  мик/камеру каждого), а не из отдельного socket-presence. socket.io отвечает за чат; чтобы
  понять, жива ли комната, сервер считает живые сокеты в ней (для чистки комнат-сирот).
- `lastActivityAt` комнаты обновляется на каждое сообщение и используется периодической
  чисткой мёртвых комнат (`jobs/cleanup.js`).

### Видеозвонки

- Кнопка «Войти в звонок» → `POST /api/rooms/:code/livekit-token` → бэк проверяет,
  что комната существует, и подписывает LiveKit-токен с грантом **только на эту комнату**
  (`roomJoin`, `canPublish`, `canSubscribe`).
- `identity` в токене = id юзера, стабильно. Это осознанно: LiveKit держит одно
  соединение на identity, поэтому вход со второй вкладки/девайса **заменяет** первое —
  «одно присутствие на аккаунт», без эха от двух микрофонов и без повисших «призраков».
- Поверх дефолтного UI LiveKit — свой аудиомикшер (Web Audio, `webAudioMix`):
  пер-участниковая громкость с бустом до 200% и мастер-громкость. Громкость 0% трактуется как
  мут (иконка/тишина), «размут» с нуля возвращает 100%.
- На каждой плитке — индикатор связи с попапом: качество (LiveKit `ConnectionQuality`),
  битрейт ↓↑ (`getStats`) и **пинг до собеседника** E2E-оценкой (как в Jitsi): прямого P2P в SFU
  нет, поэтому клиенты раз в ~3 с рассылают свой RTT до сервера по data-каналу, а показывается
  сумма плеч (мой RTT + RTT собеседника). На своей плитке — просто мой RTT до сервера.

### Секретные ссылки (zero-knowledge)

Одноразовая передача секретов (пароли, токены). **Сервер никогда не видит открытый текст или
ключ** — только шифроблоб.

```
Создание (всё в браузере):
  urlKey = 32 случайных байта  ─→ это и есть 256-битный AES-ключ (без деривации); уходит в ссылку
                                  ПОСЛЕ # (фрагмент не шлётся на сервер)
  ciphertext = AES-GCM(urlKey, iv, текст)
  на сервер: ciphertext + iv (это НЕ секреты) + TTL → сервер отвечает id

Ссылка: /secret/<id>#<urlKey>

Чтение (страница /secret/<id> показывает секрет СРАЗУ при открытии, без кнопки):
  POST /api/secrets/:id  — забрать блоб; ВСЕГДА сжигает АТОМАРНО (секрет одноразовый)
  расшифровка — в браузере ключом из #; битый ключ/повреждённые данные → AES-GCM не сойдётся
  (GET /api/secrets/:id/meta — «существует?», НЕ сжигает; остался на сервере, фронт его не дёргает)
```

- id секрета — 128 бит энтропии (`crypto.randomBytes(16)`, base64url): перебор бессмыслен.
- Открытие ссылки = получатель забирает секрет: страница сразу шлёт `POST` (consume) и
  расшифровывает. Превью-боты мессенджеров это не сожгут — они делают только GET и не выполняют
  JS, а сжигающий запрос — POST из скрипта.
- Пароля НЕТ: `urlKey` — уже полноценный случайный 256-битный ключ, растягивать (как слабый
  пароль через PBKDF2) нечего. Секрет ВСЕГДА одноразовый (сгорает после первого чтения). TTL:
  5 мин — неделя — бессрочно.
- Единственный `consume` на id гарантирован кэшем промиса на уровне модуля: повторный рендер и
  двойной mount в dev (React StrictMode) не сожгут секрет второй раз (иначе был бы ложный 404).

### Генератор ключей

Отдельный инструмент (`/keygen`, а также в тулбаре звонка и меню-скрепке чата) — случайные ключи
и пароли, генерируемые **целиком в браузере**; сервер не задействован вообще.

- Генерация: `crypto.getRandomValues` (не `Math.random`) + **rejection sampling** — равномерный
  выбор символа из алфавита без перекоса (наивный `byte % n` смещает распределение).
- Настройки: наборы символов (a–z / A–Z / 0–9 / спецсимволы), «без похожих символов» (0/O, 1/l/I),
  длина, префикс (напр. `sk-`), количество ключей за раз. Показывается примерная энтропия (бит).
- Мостик к секретке: «через секретку» отдаёт ключ(и) в форму секретной ссылки — на странице это
  навигация на `/secret`, а в звонке/чате открывается секретка **на месте** (модалкой/во вьюхе),
  чтобы не уводить из звонка.

### PWA

Клиент — устанавливаемое приложение (`vite-plugin-pwa` + Workbox).

- **Manifest** (`standalone`, тёмные цвета, иконки 192/512 + maskable + apple-touch) → Chrome/Android
  предлагают «Установить», iOS — «На экран Домой»; запускается в своём окне без адресной строки.
- **Service Worker**: precache статики (по хэшам — авто-инвалидация на деплой), `NetworkFirst` для
  `/api` (свежие данные, кэш лишь на офлайн). Realtime (socket.io, LiveKit/ws/WebRTC) SW **не
  перехватывает** — кэшировать его нельзя, сломало бы звонки.
- `registerType: 'autoUpdate'` — свежая версия доходит до пользователей сразу после деплоя.
- В dev SW выключен (`devOptions.enabled:false`), чтобы не кэшировать hot-модули; проверять —
  на сборке (`npm run build && npm run preview`).

## Защиты — полный список

### Аутентификация и сессии
- Пароли: только `bcrypt` (cost 10), хеш наружу не отдаётся никогда (`publicUser`).
- JWT в **httpOnly** cookie (XSS не украдёт) + **SameSite=Lax** (базовая защита от CSRF;
  все мутации — POST, на которые Lax cross-site cookie не шлёт).
- Срок жизни токена 7 дней, фолбэк `|| '7d'` — забытая env-переменная не породит вечные токены.
- Логин: единый ответ «Неверный email или пароль» (не раскрываем, что именно не так) +
  **dummy bcrypt.compare** при несуществующем email — тайминг ответа не выдаёт,
  зарегистрирован ли адрес.
- Rate limiting: логин — 20 **неудачных** попыток с IP за 15 мин (успешные не считаются),
  регистрация — 10 с IP в час.

### REST API
- CORS: только `CLIENT_ORIGIN`, с credentials.
- Лимит тела запроса 150 КБ (шифроблоб секрета ≤ 100 КБ + служебные поля).
- Все входные данные валидируются по типам (объект вместо строки не роняет сервер).
- 500-ки отдают только генерик «Внутренняя ошибка сервера» — `err.message` с деталями
  БД/Sequelize остаётся в серверном логе, клиенту не утекает.

### Socket.io
- Авторизация по той же httpOnly cookie в `io.use` — неавторизованное соединение отклоняется.
- `maxHttpBufferSize` 32 КБ (дефолт был 1 МБ) — мусорные пакеты режутся до обработчиков.
- `message:send`: проверка типов, непустой текст, максимум 5000 символов.
- Антифлуд: не больше 15 сообщений за 10 секунд с одного сокета.
- `room:join` — только в существующие в БД комнаты (нельзя плодить произвольные
  socket.io-комнаты в памяти).

### Секреты
- Zero-knowledge: шифрование/расшифровка только в браузере (Web Crypto API), ключ живёт
  в URL-фрагменте и на сервер не попадает физически.
- Секрет **всегда одноразовый**: сжигается **атомарно** (`DELETE` по id с проверкой числа
  удалённых строк) — два одновременных запроса не прочитают одноразовый секрет дважды.
- Протухшие секреты удаляются при обращении **и** периодической чисткой (`jobs/cleanup.js` —
  для неоткрытых ссылок, к которым никто не обратится); лимит размера 100 КБ; создание — максимум
  30 с IP в час (роут публичный — без лимита БД можно было бы забить мусором).

### Чат (хранение)
- Тексты сообщений и имена вложений шифруются **at-rest**: в PostgreSQL лежит шифротекст
  AES-256-GCM (формат `enc:v1:base64(iv‖tag‖ciphertext)`), а не открытый текст. Закрывает дамп
  БД / бэкап. Это **не** E2E — сервер держит ключ (`CHAT_ENC_KEY`) и видит текст в памяти.

### Клиент
- XSS: только React-рендеринг (автоэкранирование), `dangerouslySetInnerHTML` не используется.
- Ключи/коды генерятся через `crypto.getRandomValues` / `crypto.randomInt` — не `Math.random`.

## Осознанные решения и ограничения

- `secure: false` у cookie и `ws://` для LiveKit — **только локальная разработка**;
  на проде обязательны https, `secure: true` и wss.
- На проде сигналинг LiveKit проксируется через nginx на 443 (`wss://<домен>/livekit`), поэтому
  порт 7880 наружу не открыт; открыты только 443, 80 (TLS-renew + редирект), 22, UDP 50000-50010
  (медиа) и 7881 (TCP-фолбэк). Диаграмма ниже — про локальный `docker compose`, где 7880 прямой.
- Секреты в `livekit.yaml` и `.env.test` — дев/тестовые, в прод не идут. Реальный
  `server/.env` в git не попадает.
- `helmet` включён (защитные HTTP-заголовки). Полноценных миграций нет: схему обновляем
  `sync({ alter: true })` через `DB_ALTER` (см. «Обновление схемы БД») — осознанно для учебного проекта.
- Logout стирает cookie, но не инвалидирует сам JWT (нет чёрного списка токенов) —
  принято для учебного проекта.
- История чата — последние 100 сообщений, «подгрузить ещё» нет.
- Rate-limit хранит счётчики в памяти процесса (сбрасываются при рестарте); `app.set('trust proxy', 1)`
  включён — за реверс-прокси реальный IP берётся из `X-Forwarded-For`.
- Периодическая чистка (`jobs/cleanup.js`, `setInterval`): неактивные комнаты (по `lastActivityAt`),
  давно оффлайн temp-аккаунты (гость/одноклик) и неоткрытые протухшие секреты.

## Запуск

```bash
# 1. Инфраструктура (PostgreSQL + LiveKit)
docker compose up -d

# 2. Бэкенд
cd server
npm install
cp .env.example .env   # заполнить JWT_SECRET и LiveKit-ключи
npm run dev            # http://localhost:4000

# 3. Фронтенд
cd client
npm install
echo VITE_API_URL=http://localhost:4000 > .env
npm run dev            # http://localhost:5173
```

## Обновление схемы БД

Миграций сознательно нет. Обычный старт делает `sequelize.sync()` — создаёт недостающие таблицы,
но **не трогает существующие** (новые колонки/индексы на уже созданной БД не появятся).

Когда в модели добавили колонку или индекс — разово запусти бэкенд с `DB_ALTER=true`:

```bash
cd server
DB_ALTER=true npm run dev   # sync({ alter: true }) приведёт существующую БД к моделям, затем можно
                            # остановить и запускать обычно
```

На проде запускать осознанно (`alter` может менять/пересоздавать колонки и индексы) — схемой прода
управляет владелец сервера вручную.

## Тесты

```bash
cd server
npm test   # node:test + supertest, отдельная БД videocall_test (см. .env.test)
```

Тесты создают/дропают таблицы в `videocall_test` перед каждым тестом — основной БД не касаются.
